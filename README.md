# CheapestTickets

Клиент-серверное .NET-приложение для поиска наиболее выгодной даты вылета по заданным авиамаршрутам.

Проект разрабатывается как pet-проект для практического изучения .NET, сетевого программирования, асинхронности, работы с внешними API и базами данных.

На текущем этапе основная функциональность приложения реализована. Пользовательская часть работает в виде консольного приложения, а графический интерфейс на WPF находится в разработке.

## Возможности

На текущем этапе приложение позволяет:

* задавать несколько авиамаршрутов;
* задавать количество дней, на протяжении которых необходимо выполнить поиск;
* получать данные о стоимости перелётов через внешнее API;
* рассчитывать стоимость полного набора маршрутов для каждой даты;
* находить дату с минимальной суммарной стоимостью;
* обрабатывать несколько клиентских подключений;
* отменять длительные операции с использованием `CancellationToken`;
* обрабатывать ошибки внешнего API и отсутствие данных;
* вести логирование работы сервера;
* сохранять логи в PostgreSQL;
* сохранять историю пользовательских запросов в PostgreSQL;
* использовать общие модели данных между клиентом и сервером через отдельную библиотеку `CheapestTickets.Shared`.

### Основные компоненты

**Server**

Отвечает за серверную часть приложения:

* принимает TCP-подключения;
* создаёт контекст для каждого клиента;
* принимает и обрабатывает пользовательские запросы;
* выполняет расчёты;
* взаимодействует с внешним API;
* отменяет длительные операции при необходимости;
* отправляет результаты клиенту;
* ведёт журнал работы;
* сохраняет информацию в PostgreSQL.

**Console Client**

Текущая рабочая пользовательская часть приложения.

Отвечает за:

* получение параметров от пользователя;
* формирование запроса;
* установление соединения с сервером;
* отправку запроса;
* получение и отображение результата.

**WPF UI**

Графический интерфейс приложения, находящийся в разработке.

Планируется заменить консольный интерфейс полноценным WPF-приложением с элементами управления для выбора аэропортов, дат и других параметров запроса.

**CheapestTickets.Shared**

Отдельная библиотека с моделями, которые используются несколькими проектами.

Например:

* `FlightRequest`;
* `FlightResponse`;
* `FlightRoute`;
* `AppError` и связанные типы.

Вынесение этих моделей в отдельную библиотеку позволяет избежать дублирования одинаковых классов между клиентом и сервером.

## Принцип работы

Работа приложения начинается с пользовательской части.

Пользователь задаёт набор маршрутов и количество дней, на протяжении которых необходимо выполнить поиск.

Например:

```text
Москва → Стамбул
Стамбул → Париж
Париж → Москва

Количество дней: 10
```

Клиент формирует `FlightRequest` и отправляет его серверу по TCP-соединению.

### 1. Получение запроса

Сервер принимает подключение и создаёт `ClientContext`, содержащий информацию о конкретном клиентском соединении.

Для каждого клиента создаётся собственный контекст и `CancellationToken`, позволяющий управлять жизненным циклом запроса.

### 2. Обработка запроса

Сервер десериализует полученный JSON в общую модель `FlightRequest`.

После этого начинается расчёт стоимости.

Для каждой даты формируется набор маршрутов с соответствующей датой вылета.

### 3. Получение данных

Сервер обращается к внешнему API и получает информацию о доступных перелётах.

На основании полученных данных рассчитывается суммарная стоимость маршрутов для каждой даты.

Если для отдельного маршрута отсутствуют данные, такая дата не должна прекращать весь поиск — сервер продолжает обработку остальных дат.

### 4. Поиск минимальной стоимости

После обработки доступных дат сервер определяет дату с минимальной суммарной стоимостью и формирует `FlightResponse`.

### 5. Ответ клиенту

Результат сериализуется в JSON и отправляется обратно клиенту по TCP.

Клиент десериализует ответ и выводит пользователю найденную дату и стоимость.

## Хранение данных

Для хранения серверной информации используется **PostgreSQL**.

В базе данных предусмотрены отдельные таблицы для:

### Логов

Сохраняется информация о событиях приложения, включая:

* запуск и остановку сервера;
* подключения клиентов;
* начало расчёта;
* отправку результатов;
* отключение клиентов;
* ошибки.

Логи содержат время события, источник, информацию о клиенте и сообщение.

### Истории пользовательских запросов

Сохраняется информация о выполненных запросах пользователей.

История предназначена для последующего анализа работы приложения и получения статистики.

## Запуск проекта

Для запуска проекта необходимо:

1. Установить подходящую версию **.NET SDK**.
2. Установить **PostgreSQL**.
3. Создать базу данных проекта.
4. Настроить строку подключения к PostgreSQL.
5. Запустить сервер.
6. После запуска сервера запустить клиент.

Сервер должен быть запущен до начала работы клиентской части.

### Конфигурация

Настройки подключения к базе данных и другие параметры приложения находятся в конфигурационных файлах проекта.

Секретные данные, такие как пароли и API-ключи, не должны храниться непосредственно в репозитории.

## Использование

### Консольный клиент

После запуска клиент предлагает пользователю ввести необходимые параметры.

После отправки запроса сервер выполняет расчёт и возвращает результат.

В случае успешного выполнения пользователь получает информацию примерно следующего вида:

```text
Дешевле всего вылетать 2025-11-02 - 83985 руб.
```

Если сервер не смог получить ответ:

```text
Не удалось получить ответ от сервера
```

Если сервер вернул ошибку:

```text
Сервер вернул ошибку: ...
```

Если подходящих данных нет:

```text
Не получилось найти подходящие маршруты
```

## Обработка ошибок

В проекте используется типизированное представление ошибок `AppError`.

Основные типы ошибок:

```text
None
NoData
ApiUnavailable
Timeout
InvalidRequest
Internal
```

Это позволяет отделять тип ошибки от текста сообщения и обрабатывать различные ситуации независимо друг от друга.

Например:

* `NoData` — внешнее API не предоставило данные;
* `ApiUnavailable` — внешний API недоступен;
* `Timeout` — операция превысила допустимое время;
* `InvalidRequest` — некорректный запрос пользователя;
* `Internal` — внутренняя ошибка приложения.

---

## Отмена операций

Длительные операции используют `CancellationToken`.

Это позволяет серверу прекратить выполнение расчёта, когда дальнейшая обработка запроса больше не требуется.

Механизм отмены используется, в частности, при завершении жизненного цикла клиентского соединения.
